# Project Context

## Glossary

- **Auto-Crop**: Local-first runtime that coordinates installed AI coding agents as a small operating company.
- **CEO Agent**: The user-selected local agent, such as Claude Code or Codex, that converts founder input into a company blueprint.
- **Founder Vision**: The user's natural-language description of what the company should build or pursue.
- **Interface Locale**: The language setting that controls all user-facing Auto-Crop UI chrome and system-authored labels. Interface Locale is separate from raw source content such as user-provided company names, Founder Vision text, CEO Intake text, URLs, file paths, command output, and agent brand names.
- **Localized Business Content**: User-facing business content authored by Auto-Crop or its agents, such as department names, department responsibilities, objective titles, task titles, task descriptions, progress labels, system activity messages, and localized summaries of agent output. Localized Business Content must be rendered in the active Interface Locale rather than treated as static English UI text. _Avoid_: frontend-only translation, machine-translated display string.
- **CEO Intake**: A post-creation natural-language input submitted by the user to CEO Office. A CEO Intake can describe a new vision, task, material, constraint, or direction. It is appended to company context for CEO evaluation and planning; it does not overwrite the original Founder Vision.
- **Permission Mode**: Runtime policy level for local execution. Current values are `safe`, `balanced`, and `autonomous`. It decides both whether a task needs Founder Approval before dispatch and which Runtime Capabilities its Agent Capability Grant may contain.
- **Runtime Capability**: What a process is *permitted to do* during one Agent Run — `workspace_read`, `workspace_write`, `run_command`, `web_research`. Distinct from the agent capabilities (`code`, `research`, …) that select which agent runs a task: those describe what an adapter is good at. _Avoid_: required capability, tool, permission.
- **Task Capability Needs**: The Runtime Capabilities a task needs to be doable at all, derived from its proof schema and required capabilities. Intersected with Permission Mode to produce the grant; need and policy are an intersection, never a maximum. _Avoid_: requiredCapabilities, agent skills.
- **Agent Capability Grant**: The explicit set of Runtime Capabilities the runtime hands one Agent Run, and the ones it needed and was refused. Passed to the agent process as launch flags, stated in the prompt, and part of an Agent Session's identity. Nothing is inherited from the operator's machine and nothing about it is discovered mid-run — an agent that meets a denial it was not told about will narrate it as an environment limitation and degrade its deliverable rather than report it (ADR 0021). _Avoid_: sandbox, allowed tools, permission mode.
- **Structured Output Contract**: A JSON Schema the runtime attaches to an Agent Run so the CLI enforces the reply's shape, instead of the prompt asking for it and the parser hoping. Declared for any run whose output the runtime must parse. A reply that misses it fails as `invalid_agent_output`, never as `agent_failed`: the process answered, and the contract was the runtime's (ADR 0022). _Avoid_: output format instruction, prompt rule, response parser.
- **Grant Refutation**: The runtime rejecting an Environment-Blocked Blocker that names a capability the run was granted. The mirror of the Reachability Snapshot: runtime-held evidence that refutes a claim, rather than confirming one the agent could not prove. Only capabilities the runtime actually grants are refutable. _Avoid_: artifact validation, blocker review.
- **Company Blueprint**: The structured result returned by the CEO Agent, including company metadata, departments, objectives, key results, proof schemas, and first tasks.
- **Company Creation**: A durable process representing a user-requested company while the CEO Agent is producing its Company Blueprint. It starts before departments or tasks exist and ends when the company becomes a draft or records a creation failure. _Avoid_: synchronous create request, blueprint cache.
- **Creating Company**: A company whose creation has been accepted but whose Company Blueprint has not yet been written. _Avoid_: draft company, hidden pending request.
- **Creation-Failed Company**: A company whose Company Creation could not produce a valid Company Blueprint but remains available for diagnosis and retry. _Avoid_: deleted failed request, ordinary runtime failure.
- **Creation Progress Event**: A user-facing event describing Company Creation progress before ordinary task activity exists. _Avoid_: task event, fake task.
- **Creation Idempotency Key**: A client-generated identity for one submitted Company Creation so refreshes, retries, network interruptions, and duplicate clicks resolve to the same company. _Avoid_: company name dedupe, global duplicate detection.
- **Creation Attempt**: One run of the CEO Agent trying to produce a Company Blueprint for a Company Creation. A Company Creation may have multiple attempts over time, but only one active attempt at once. _Avoid_: duplicate company, parallel blueprint race.
- **Company Event**: A durable company-level activity entry that is not tied to a task, such as Company Creation progress. _Avoid_: task event with a fake task id.
- **Agent Output**: The raw stdout/stderr content and workspace side effects produced by an agent run. Agent Output can be useful evidence for humans, but it is not itself a completed task deliverable unless the runtime captures it as Proof.
- **Execution Brief**: The founder-facing statement of purpose, approach, and expected outcome an agent produces in a planning-only run before the substantive work prompt is dispatched. It is durable evidence of intent, not a deliverable, and it holds no capabilities: its run is launched with no tools and a Structured Output Contract. _Avoid_: Task Brief, execution plan, Execution Report.
- **One-shot Agent Run**: An Agent Run executed by starting a fresh agent process for one task attempt, then ending that process when the attempt finishes. _Avoid_: stateless task, cold run.
- **Agent Session**: A reusable agent context container that may serve multiple Agent Runs for the same company, agent, Permission Mode, and Agent Capability Grant. An Agent Session can improve continuity, but it does not decide whether a task is complete. The grant is part of its identity because a session is a live process holding the capabilities it was started with.
- **Session Memory**: Context remembered inside an Agent Session. Session Memory is not Proof, Consumable Proof, a Task Deliverable, or a Handoff Package. _Avoid_: hidden proof, implicit handoff.
- **Session Policy**: Runtime rules that decide whether an Agent Run is eligible to attempt an Agent Session. Session Policy is separate from Proof Schema, which defines the required deliverable.
- **Task Deliverable**: The artifact a task must produce to be eligible for review. A Task Deliverable must be represented by Proof that matches the task's proof schema.
- **Proof**: A runtime-recorded artifact, command output, URL, screenshot, diff, deployment, or other accepted evidence that satisfies a task's proof schema. Tasks without Proof are not complete, even when the agent produced useful Agent Output.
- **Proof Schema**: The contract for a task's required deliverable, defining which Proof Types the runtime will accept as evidence the task is done. Every Proof Schema offered to CEO planning must be a Collectable Proof Schema. _Avoid_: proof file, checklist, Artifact Payload Schema.
- **Collectable Proof Schema**: A Proof Schema the runtime can actually satisfy, meaning it has a collector path that turns workspace files or command output into recorded Proof of an accepted type. A Proof Schema with no collector path is a landmine: tasks using it can never complete and loop until the Bounded Recovery ceiling. Enforced by a registration test and a runtime filter on the CEO planning menu. _Avoid_: advertised proof schema, planner menu entry.
- **Business Artifact**: A structured, runtime-validated business handoff derived from Proof and stored in Auto-Crop state. Business Artifacts are the only normal inputs that downstream tasks may consume. _Avoid_: proof file, markdown brief, raw agent output.
- **Artifact Kind**: The workflow behavior of a Business Artifact, such as `deliverable`, `blocker`, `decision_request`, `direction_change_request`, or `final_report`. Artifact Kind decides which queue or gate handles the artifact. _Avoid_: business topic, proof schema.
- **Artifact Role**: The generic handoff role of a deliverable Business Artifact, such as `findings`, `plan`, `spec`, `implementation`, `validation`, or `launch`. Artifact Role is stable across playbooks and should not contain use-case names. _Avoid_: keyword research, MVP brief, department name.
- **Artifact Subtype**: The task-specific or playbook-specific business topic of a Business Artifact, such as `keyword_research`, `customer_interview_summary`, `pricing_scan`, or `seo_launch_plan`. Artifact Subtype may be unregistered without blocking structural validation. _Avoid_: artifact kind, artifact role.
- **Task Type**: The semantic kind of work a task performs, such as `research.seo_keyword_opportunity` or `product.mvp_brief`. Task Type chooses the expected Artifact Kind, Artifact Role, and payload schema. _Avoid_: task title, proof schema.
- **Artifact Payload Schema**: The task-type or playbook-specific validation rules for a Business Artifact payload. The first implementation may use a code registry, but the model should allow playbook-level configuration later. _Avoid_: markdown checklist.
- **Artifact Validation**: The deterministic runtime check that a Business Artifact has the expected kind, role, required payload fields, valid lineage, no blocker signal, and no unapproved direction drift. A valid artifact can still carry a Verification Verdict that is not `passed`. _Avoid_: CEO review, proof capture, verification verdict.
- **Blocker Report**: A diagnostic Business Artifact produced when an agent cannot create the expected deliverable, such as because an upstream handoff is missing or unreadable. A Blocker Report is visible to users and CEO Office, but it is not consumable by ordinary downstream tasks. _Avoid_: failed product brief, normal proof.
- **Environment-Blocked Blocker**: A Blocker Report of class `environment_blocked`, produced when an agent cannot use a capability the environment does not provide, such as a headless browser, container, or display. When the agent also declares a runtime-checkable claim and the runtime confirms it — by a live check when the claimed URL is still reachable, otherwise against a Reachability Snapshot from the same Agent Run — the task degrades to a deliverable with a recorded `validationLimits` caveat naming which path confirmed it, instead of failing. A blocker naming a capability the run's Agent Capability Grant actually contained is refuted instead: the task fails, naming the contradiction. _Avoid_: sandbox error, capability failure, agent excuse.
- **Local Prototype Server**: The `python3 -m http.server` or framework preview server an agent starts inside a task workspace to serve a runnable prototype. It is agent-owned: nothing in the runtime manages its lifecycle, so it may not be listening when a later Agent Run verifies a claim against it. _Avoid_: dev server, static server, runtime-managed server.
- **Reachability Snapshot**: The HTTP status a claimed local URL returned when the agent fetched it during a runtime-controlled Agent Run, recorded in the blocker artifact and used to confirm the claim when the URL is unreachable at verification time rather than re-fetching it then. A Reachability Snapshot is trusted on the same basis as other Proof recovered from a controlled task workspace; an equivalent claim with no Agent Run behind it is not, and a live non-2xx response overrides it. _Avoid_: live fetch result, ping, health check.
- **Direction Change Request**: A Business Artifact requesting an explicit change to a prior accepted business decision, such as changing the selected market, keyword, product category, MVP type, or launch target. Direction changes require Founder Approval before downstream work can consume the changed direction. _Avoid_: implicit pivot, engineering adjustment.
- **Founder Approval**: The user's explicit yes/no consent for a high-impact action already proposed, including changing an already-accepted market or keyword, changing the MVP type, Engineering changing product direction, publishing to a public URL, submitting Google Search Console or sitemap actions, spending money, or connecting ads, affiliate accounts, or API keys. _Avoid_: CEO review, Founder Decision.
- **Founder Decision**: A choice reserved for the human founder that a completed task's output surfaces: several viable options for a Strategic Decision Kind that has no fixed value yet. The runtime and CEO Agent must not resolve it. A deliverable carrying an unresolved Founder Decision does not auto-accept; the founder picking an option is itself the acceptance of that deliverable, and when a task surfaces more than one, the deliverable is accepted (with `founder_decision` acceptance provenance) only once every one is resolved. The founder can instead reject every option and return the task to the department with a reason, which discards the picks recorded for that task. An unresolved Founder Decision is a CEO Attention Item and makes its downstream tasks read as "waiting on decision". _Avoid_: CEO Decision, Founder Approval, review request.
- **Founder Decision Resolution**: The record of how the founder settled one Founder Decision — a picked option, or a return with a Review Return Reason and note. Keyed by the Founder Decision's projected id, it fills the projection's `status` / `resolvedOption` / `resolvedAt`. A return discards every recorded pick for the task. _Avoid_: CEO Review Decision, approval.
- **Strategic Decision Kind**: One of a fixed, playbook-neutral set of business decisions whose first value is the founder's to set, such as the target market, the product direction, the MVP type, the pricing model, or the launch target. An agent declares an open choice against a Strategic Decision Kind and the runtime turns it into a Founder Decision; a choice outside the set is the agent's own call. _Avoid_: inherited decision field, task-specific option.
- **Founder Decision Briefing**: The required prose field on a Founder Decision that carries the substance the founder needs to decide from the Decision card alone: what was explored, where the opportunity is, what is differentiated, the monetization angle, and why these options exist. Authored by the completing agent in the company canonical locale and declared alongside `options` / `recommendation` / `rationale` in `open_decisions`; a known-kind entry without it is a structural validation failure. It is what makes the Decision card the post-task substance surface, as opposed to the Task Outcome Summary (a whole-task conclusion carried on the Task Completion Event) or the Execution Report (the four-field structured result of any deliverable). _Avoid_: Task Outcome Summary, Execution Report, rationale.
- **Parent Proof Summarization**: The step where a parent task uses ready department subtask Proof to produce the parent-level Proof that can be reviewed by CEO Office. _Avoid_: automatic proof merge, subtask approval.
- **Proof Recovery**: A user-triggered or runtime-triggered attempt to turn existing Agent Output inside a controlled task workspace into recorded Proof after the original Agent Run finished without Proof. Proof Recovery must still satisfy the task's proof schema and must not treat arbitrary workspace files as completion. _Avoid_: auto-approval, hidden completion.
- **Task Recovery Request**: A user-triggered or runtime-triggered attempt to restart progress after a task failed, timed out, or became stale while running. A Task Recovery Request may requeue the original task when no Partial Output exists, or create a follow-up task from Partial Output when useful output exists. It is not Proof Recovery and it does not make work complete without Proof and CEO review.
- **CEO Review Request**: A department-submitted request for CEO Office to approve or return a valid, reviewable deliverable after execution. Departments can submit and track CEO Review Requests, but CEO Office owns the approve/return decision. Invalid artifacts, Blocker Reports, and decision requests are visible to CEO Office through separate queues, but they are not CEO Review Requests.
- **CEO Review Queue**: The CEO Office queue for tasks carrying an open `awaiting_ceo_review` Task Hold, whose Business Artifact is valid, current, unreviewed, and of Artifact Kind `deliverable` or `final_report`. The Hold is what makes the decision offerable — an artifact that still reads unreviewed on a task that has left review is not in the queue (ADR 0020). _Avoid_: all review-status tasks, blocked queue, artifact review status alone.
- **CEO Decision Queue**: The CEO Office queue for Business Artifacts whose Artifact Kind asks for a decision, including ordinary decision requests and direction change requests. _Avoid_: deliverable review, artifact validation.
- **CEO Blocked Queue**: The CEO Office queue for tasks or Business Artifacts that cannot be reviewed because the artifact is missing, invalid, stale, blocked, or otherwise not reviewable. _Avoid_: review queue, approval queue.
- **Checkpoint CEO Review Request**: A CEO Review Request for an intermediate decision during task execution. Approval means the department may continue execution; it does not complete the task.
- **Completion CEO Review Request**: A CEO Review Request for final task acceptance. Approval means the task's submitted work is accepted and the task can be marked complete.
- **CEO Review Decision**: A durable CEO Office decision on a CEO Review Request. A decision can approve the work or return it with a structured reason and optional note. CEO approval accepts ordinary task work; it is not a substitute for Founder Approval when a direction change or external launch action needs user consent.
- **Review Return Reason**: A structured reason CEO Office chooses when returning a CEO Review Request. Current reasons are needs changes, unclear task definition, scope too large, and wrong direction.
- **Partial Output**: Useful Agent Output left behind by a failed or timed-out task. Partial Output should remain visible for diagnosis and follow-up, but it does not make the task complete.
- **Task Execution Profile**: A task execution contract that sets the expected time budget and failure explanation style for a task based on its deliverable shape, raised to a floor when the run's Agent Capability Grant carries a capability whose wall-clock cost the deliverable shape does not predict — `web_research` today. It is part of how Auto-Crop decides how long an agent should be allowed to work before the run is considered failed.
- **Effective Timeout**: The final timeout budget actually enforced for an Agent Run after Task Execution Profile and environment override rules are resolved. _Avoid_: displayed budget, requested timeout.
- **Task Execution Summary**: The latest durable outcome facts shown on a task, including failure reason, failure message, execution profile, and Effective Timeout. _Avoid_: activity text, run log, Task Outcome Summary.
- **Task Outcome Summary**: The natural-language summary a completing agent produces for a task: the conclusion it reached, what that means for the objective it serves, what gap remains, and, when there is a Founder Decision, the options with their trade-offs and the agent's recommendation. Carried on the Task Completion Event. _Avoid_: Task Execution Summary, Agent Output, run log.
- **Task Brief**: A CEO Office Item that introduces a task at the macro business level before execution: why it is being done, what outcome is expected, how it links to the Founder Vision or objective, and what dependencies shape it. _Avoid_: task log, agent run start, implementation plan.
- **Execution Report**: A CEO Office Item that summarizes a completed task in structured business language: execution conclusion, meaning for the Founder Vision or objective, remaining gap, and recommendation. _Avoid_: Task Execution Summary, proof details, raw agent output.
- **Task Dependency**: A relationship where one task can only run after another task has an accepted, current, valid Business Artifact matching the downstream task contract. Each carries a Dependency Input Role. _Avoid_: task order, follow-up note, review-ready proof.
- **Dependency Input Role**: What a Task Dependency supplies to its consumer: `context` (ordinary upstream input, the default), `verification_requirements` (the requirements the consumer verifies), or `verification_target` (the output the consumer verifies, handed over as a snapshot). _Avoid_: dependency type, edge label.
- **Verification Contract**: The rule that a verifying task checks a runtime-made snapshot of its `verification_target` producers against the requirements declared by its `verification_requirements` producer, reporting one check per requirement. See ADR 0023. _Avoid_: validation prompt, test instructions.
- **Planned Verification**: The `verification` declaration every task in a CEO blueprint carries: `null`, or the earlier tasks it verifies and the requirements it verifies them against. It is how a verifier the CEO plans comes under the Verification Contract; the runtime never infers verification duty from a task's proof schema. See ADR 0025. _Avoid_: validation task, test task.
- **Verification Rework**: What the runtime does about a Verification Verdict that did not pass, recorded once per failed report: rework the faulted producers with the failed checks as feedback, re-verify output that has since changed, escalate what re-producing cannot fix, or stop when the round budget is spent. The budget is three verification rounds per verifying task; only a replan starts a new one. See ADR 0026. _Avoid_: retry, Bounded Recovery attempt.
- **Verification Verdict**: The runtime-derived outcome of a Verification Contract — `passed`, `failed`, or `inconclusive` — recorded on the verifier's Business Artifact with the target revisions it covers. Only `passed` lets the artifact stand as a successful delivery; it is never read from prose. _Avoid_: validation status, report conclusion.
- **Department Subtask Readiness**: The point where a department-created subtask can be consumed by its parent and its siblings: it is in `review` or `complete`, has Proof and a current valid deliverable, carries no Verification Verdict other than a still-current `passed`, and is held by nothing but its Internal Delivery Hold. It is department-internal readiness, not CEO Office acceptance, and a task outside the parent cannot consume on it. See ADR 0024. _Avoid_: subtask approval, parent completion, review plus proof.
- **Internal Delivery Hold**: The `awaiting_parent_aggregation` Task Hold a delivered department subtask sits under in `review`. Owned by the runtime and ended when the parent's result is accepted; it never offers a CEO decision. _Avoid_: CEO review hold, subtask approval.
- **CEO Task Dependency Graph**: A CEO Workspace projection that shows first tasks by owning department, user-facing status, and real Task Dependencies so the user can see what is blocked and where to inspect next. It is read-only and does not show department subtasks by default. _Avoid_: task list, department progress flow, editable task graph.
- **CEO Reassignment Request**: A department-submitted request asking CEO Office to clarify, split, replan, or reassign a task before or during execution. It is not a CEO Review Request because no Task Deliverable is being approved.
- **Consumable Business Artifact**: A Business Artifact that is current, valid, accepted through CEO Office review, not stale, not a Blocker Report, and not blocked by an unapproved Direction Change Request. _Avoid_: consumable proof, promising stdout, informal result.
- **Legacy Artifact Type Compatibility**: Temporary runtime support for reading the old `artifactType` field while the model migrates to Artifact Kind, Artifact Role, and Artifact Subtype. Compatibility lasts through the migration that adds the new persisted fields plus one cleanup migration. _Avoid_: permanent alias table.
- **Dependency Readiness**: The single decision, shared by dispatch, Parent Task Aggregation, the dependency cascade and Hold reconciliation, that every direct upstream dependency can be consumed: ordinary dependencies need accepted, current, valid Business Artifacts; internal ones need Department Subtask Readiness. _Avoid_: dependency status check, proof existence check, aggregation readiness.
- **Dependency Cascade**: Runtime propagation that re-evaluates direct downstream tasks after an upstream task's Business Artifact is accepted by CEO Office, moving dependency-blocked tasks back to `queued` when all dependencies are ready. _Avoid_: manual refresh, automatic execution.
- **Bounded Recursive Cascade**: A Dependency Cascade that may continue through longer downstream dependency chains up to a fixed depth while preventing repeated visits to the same task. _Avoid_: unlimited cascade, scheduler wakeup.
- **Scheduler Wake Request**: A runtime hint asking the scheduler loop to tick sooner because dependency-derived work has become `queued`. It does not execute tasks, change Dependency Readiness, or bypass scheduler locking. _Avoid_: cascade execution, direct task run.
- **Task Completion Event**: A durable company-state change recorded when a task produces an accepted or blocked outcome, including the task's department ownership, Business Artifact, Task Outcome Summary, dependency impact, remaining gaps, and proposed Next Step Items. It is recorded for every task completion path, but it does not always become a CEO Attention Item. _Avoid_: approval notification, task log line.
- **CEO Office Item**: A macro business signal projected into CEO Office from company facts, such as a Task Brief, decision request, approval request, Human Action, Wait State, Blocked Issue, Execution Report, Objective Stage Change, Decision Resolution, or Final Founder Report. _Avoid_: task event, notification, raw department report.
- **CEO Office Timeline**: The global chronological view of CEO Office Items that have happened, showing macro task flow and company-state changes without low-level execution events. _Avoid_: agent activity log, task detail view, future roadmap.
- **CEO Attention Item**: A task or company-state item that should interrupt or prominently surface in CEO Office because it contains an exception, decision point, unresolved Founder Decision, human action, cross-department impact, goal-stage change, or executive summary. _Avoid_: every completed task, review request.
- **CEO Attention Rollup**: A CEO Office projection that groups related CEO Attention Items by Founder Vision, objective, or dependency chain so the user sees the business situation instead of a stream of isolated task notifications. _Avoid_: notification feed, flat inbox.
- **Next Step Item**: A structured recommendation emitted from a Task Completion Event describing what must happen next for the relevant Founder Vision, objective, or dependency chain to keep progressing. A Next Step Item may become an automatic downstream task, a human action, a founder decision, a decision request, a wait state, a downstream handoff, or a vision gap. _Avoid_: freeform next steps note.
- **Decision Resolution**: A CEO Office Item recording that a previously pending decision, approval, or return choice was settled, preserving when the choice happened in the CEO Office Timeline. _Avoid_: new decision request, Execution Report, task completion.
- **Automatic Acceptance**: Runtime acceptance of a Business Artifact without manual CEO Review, and the default path for internal deliverables. It applies when the current artifact is valid and reviewable, its text does not match the deterministic external-or-sensitive risk patterns, no Founder Approval action is involved, and it carries no unresolved Founder Decision. Task risk level is a planning hint, not a gate. Automatic Acceptance still records a Task Completion Event. _Avoid_: auto-approval, unchecked completion, opt-in acceptance.
- **Next Step Routing**: Runtime handling that turns each Next Step Item into its proper follow-up surface, such as a queued downstream task, Human Action, CEO Decision Queue item, Wait State, downstream handoff, or Vision Gap. Departments may propose Next Step Items, but runtime validation and routing decide how they affect company state. _Avoid_: create every next step as a task, advice-only summary.
- **Human Action**: A Next Step Item that Auto-Crop cannot complete itself because it requires a person to use an external account, grant permission, deploy publicly, pay, sign, approve, or otherwise act outside the runtime. Human Actions should be visible in CEO Office, block only downstream work that truly depends on the action, and may require Founder Approval when they affect external launch, spend, credentials, or public publishing. _Avoid_: blocked task, manual TODO.
- **Human Action Confirmation**: The user-submitted evidence that a Human Action was completed, such as a URL, account state, receipt, approval note, or configuration value. The runtime should verify the evidence when possible and convert it into the appropriate Business Artifact, Task Completion Event, or unblocked dependency state. _Avoid_: trust me checkbox, agent guess.
- **Wait State**: A Next Step Item where progress depends on an external delay or result, such as search indexing, customer response, third-party review, traffic accumulation, or scheduled observation. A Wait State is not an execution failure. _Avoid_: blocked task, idle task.
- **Vision Gap**: A remaining gap between a completed task's Business Artifact and the Founder Vision or objective it serves. Vision Gaps explain why a task can be complete while the broader business outcome is not yet achieved, and they may be informational, blocking, or strategic. _Avoid_: task failure, missing proof.
- **Task Hold**: The persisted record of why a task stopped, who can clear it, and which record it waits on — a Business Artifact, Human Action, Founder Decision, Approval, Wait State, upstream task, or Agent Run. A task in a Held Task Status always has at least one open Hold, and a task the runtime is carrying has none. Holds are the single source of truth for "this task is parked": CEO Office offers a review decision from an open `awaiting_ceo_review` Hold, never from a Business Artifact's review status (ADR 0020). _Avoid_: blocked status, dependency note, blocked queue entry.
- **Held Task Status**: A task status that means "stopped, waiting on something" — `waiting_dependency`, `blocked`, `review`, `needs_replan`, `failed` — as opposed to the self-propelling statuses the runtime carries on its own (`queued`, `running`, `retrying`) and the terminal ones (`complete`, `cancelled`). _Avoid_: blocked, paused, idle.
- **Resume Affordance**: An action some actor can take right now to move a stopped task forward, computed server-side from its open Task Holds and offered to every surface and checked by every API guard. Every Task Hold kind offers at least one Resume Affordance other than cancelling, and every Resume Affordance is honoured by a route that performs it — an offered action nothing performs is worse than none. _Avoid_: button, enabled action, recovery eligibility.
- **Task Transition Seam**: `applyTaskTransition`, the only code permitted to write a task's status. It opens the Task Hold a parked task needs and resolves the Holds the new status makes untrue, so status and Holds cannot drift apart. _Avoid_: status update, state setter.
- **Bounded Recovery**: Automatic task recovery that changes execution conditions and has a hard stop, such as escalating an Effective Timeout before requiring replanning, or a per-task attempt ceiling after which the task terminates as `retry_exhausted` and is routed to the CEO Blocked Queue instead of being re-queued again. _Avoid_: infinite retry.
- **Replan Required**: A task outcome where the current task is too broad or expensive for the available execution profile and should be split or rewritten before downstream work continues. _Avoid_: timeout failure.
- **Agent Activity**: Durable, user-facing timeline entries that explain task execution progress and outcomes. _Avoid_: debug log, raw stdout.
- **Emergency Stop**: The user-facing command that stops active Agent Runs and active Agent Sessions for a company without deleting queued tasks. _Avoid_: normal pause, task cancellation.
- **Artifact Workspace**: The workspace whose files are treated as the task's runnable or inspectable product. A dependent validation task may use another task's Artifact Workspace when validating that task's output. _Avoid_: task folder, temp folder.
- **Dependency Block**: A task state caused by an unmet or failed Task Dependency, distinct from an agent execution failure. _Avoid_: failed validation, skipped task.
- **Artifact Lineage**: The explicit chain of Business Artifacts and source decisions a task consumed, such as Founder Vision to Research findings to Product MVP brief to Engineering implementation to Growth launch plan. Downstream tasks must preserve lineage and may not silently swap business direction. _Avoid_: hidden context, workspace history.
- **Direction Drift**: A mismatch between a downstream Business Artifact and the accepted upstream business decisions it claims to implement. For example, an Engineering artifact implementing an image cropper when the accepted Product artifact specifies a JSON-to-CSV converter. Direction Drift blocks downstream consumption unless covered by an approved Direction Change Request. _Avoid_: creative interpretation, implementation detail.
- **Final Founder Report**: The CEO-Agent-authored, company-keyed record produced when a company reaches Company Quiescence. It states the original Founder Vision, the actual result in plain language, each department's inputs and outputs, goal fit, remaining Vision Gaps, and a recommended next step, and classifies the outcome as `achieved`, `stalled`, or `waiting`. It is its own record, not a Business Artifact (a Business Artifact is task-bound; a report is not). It is versioned by `isCurrent`: quiescence reached again after new work has run produces a new report. If the authoring agent run fails past its retry ceiling, a deterministic report is assembled from Company State Snapshot data instead. _Avoid_: review list, activity feed summary, the `summarizeFounderReport` projection alone, `final_report` Business Artifact.
- **Company Quiescence**: The computed state in which a company has no forward move left: no task is `queued`, `running`, or `waiting_dependency`, no Wait State checks in within the near horizon, and every remaining task is terminal or parked on a Human Action or Founder Decision. Reaching Company Quiescence triggers a Final Founder Report. It is not a persisted company status. _Avoid_: all tasks complete, company finished, paused company.
- **Objective Stage Change**: A CEO Attention Item raised when the last task rolling up to an objective reaches a terminal state, condensing that objective's Task Outcome Summaries and key-result status into one runtime-assembled summary. It is the per-objective middle signal between the silent routine task completion and the whole-company Final Founder Report, and it does not run an agent. _Avoid_: per-task notification, key result update line, CEO Attention Rollup of routine work.
- **Parent Task Aggregation**: Runtime aggregation that applies Dependency Readiness to a parent task with department subtasks. It can queue the parent for proof summarization when all dependencies are ready, or block the parent when a dependency is blocked, failed, missing its deliverable, or needs replanning. It has no readiness rule of its own. _Avoid_: scheduler wakeup, automatic proof generation.
- **Company State Snapshot**: The persisted company, department, objective, task, proof, and review state needed to rebuild the dashboard after a refresh. _Avoid_: blueprint cache, frontend state.
- **Onboarding Wizard**: The sequential setup flow shown before a company is created. It collects company name, CEO Agent, Founder Vision, and Permission Mode one step at a time.
- **Creation Loading Page**: The CRT-styled intermediate page shown after `Create Company` while the backend waits for the CEO Agent to produce a blueprint.
- **Department Workspace**: The post-creation default view that shows a left rail of `CEO` plus generated departments, and a right-side role workspace for the selected role.
- **Reusable Retro UI**: Existing dashboard primitives under `apps/dashboard/src/ui/`, including `AppShell`, `PageHeader`, `Workspace`, `RetroPanel`, `RetroButton`, `RetroField`, `RetroTextarea`, `RetroSelect`, `RetroListRow`, `RetroBadge`, `RetroStatus`, `VideotexLog`, and `VideotexKeyValue`.

## UI Implementation Rule

New dashboard flows must reuse existing reusable retro components wherever possible. Create new UI primitives only when the existing component set has a clear gap, and prefer small composition components over new styling systems.
