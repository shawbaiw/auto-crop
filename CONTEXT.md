# Project Context

## Glossary

- **Auto-Crop**: Local-first runtime that coordinates installed AI coding agents as a small operating company.
- **CEO Agent**: The user-selected local agent, such as Claude Code or Codex, that converts founder input into a company blueprint.
- **Founder Vision**: The user's natural-language description of what the company should build or pursue.
- **Interface Locale**: The language setting that controls all user-facing Auto-Crop UI chrome and system-authored labels. Interface Locale is separate from raw source content such as user-provided company names, Founder Vision text, CEO Intake text, URLs, file paths, command output, and agent brand names.
- **Localized Business Content**: User-facing business content authored by Auto-Crop or its agents, such as department names, department responsibilities, objective titles, task titles, task descriptions, progress labels, system activity messages, and localized summaries of agent output. Localized Business Content must be rendered in the active Interface Locale rather than treated as static English UI text. _Avoid_: frontend-only translation, machine-translated display string.
- **CEO Intake**: A post-creation natural-language input submitted by the user to CEO Office. A CEO Intake can describe a new vision, task, material, constraint, or direction. It is appended to company context for CEO evaluation and planning; it does not overwrite the original Founder Vision.
- **Permission Mode**: Runtime policy level for local execution. Current values are `safe`, `balanced`, and `autonomous`.
- **Company Blueprint**: The structured result returned by the CEO Agent, including company metadata, departments, objectives, key results, proof schemas, and first tasks.
- **Agent Output**: The raw stdout/stderr content and workspace side effects produced by an agent run. Agent Output can be useful evidence for humans, but it is not itself a completed task deliverable unless the runtime captures it as Proof.
- **One-shot Agent Run**: An Agent Run executed by starting a fresh agent process for one task attempt, then ending that process when the attempt finishes. _Avoid_: stateless task, cold run.
- **Agent Session**: A reusable agent context container that may serve multiple Agent Runs for the same company, agent, and Permission Mode. An Agent Session can improve continuity, but it does not decide whether a task is complete.
- **Session Memory**: Context remembered inside an Agent Session. Session Memory is not Proof, Consumable Proof, a Task Deliverable, or a Handoff Package. _Avoid_: hidden proof, implicit handoff.
- **Session Policy**: Runtime rules that decide whether an Agent Run is eligible to attempt an Agent Session. Session Policy is separate from Proof Schema, which defines the required deliverable.
- **Task Deliverable**: The artifact a task must produce to be eligible for review. A Task Deliverable must be represented by Proof that matches the task's proof schema.
- **Proof**: A runtime-recorded artifact, command output, URL, screenshot, diff, deployment, or other accepted evidence that satisfies a task's proof schema. Tasks without Proof are not complete, even when the agent produced useful Agent Output.
- **Business Artifact**: A structured, runtime-validated business handoff derived from Proof and stored in Auto-Crop state. Business Artifacts are the only normal inputs that downstream tasks may consume. _Avoid_: proof file, markdown brief, raw agent output.
- **Artifact Kind**: The workflow behavior of a Business Artifact, such as `deliverable`, `blocker`, `decision_request`, `direction_change_request`, or `final_report`. Artifact Kind decides which queue or gate handles the artifact. _Avoid_: business topic, proof schema.
- **Artifact Role**: The generic handoff role of a deliverable Business Artifact, such as `findings`, `plan`, `spec`, `implementation`, `validation`, or `launch`. Artifact Role is stable across playbooks and should not contain use-case names. _Avoid_: keyword research, MVP brief, department name.
- **Artifact Subtype**: The task-specific or playbook-specific business topic of a Business Artifact, such as `keyword_research`, `customer_interview_summary`, `pricing_scan`, or `seo_launch_plan`. Artifact Subtype may be unregistered without blocking structural validation. _Avoid_: artifact kind, artifact role.
- **Task Type**: The semantic kind of work a task performs, such as `research.seo_keyword_opportunity` or `product.mvp_brief`. Task Type chooses the expected Artifact Kind, Artifact Role, and payload schema. _Avoid_: task title, proof schema.
- **Artifact Payload Schema**: The task-type or playbook-specific validation rules for a Business Artifact payload. The first implementation may use a code registry, but the model should allow playbook-level configuration later. _Avoid_: markdown checklist.
- **Artifact Validation**: The deterministic runtime check that a Business Artifact has the expected kind, role, required payload fields, valid lineage, no blocker signal, and no unapproved direction drift. _Avoid_: CEO review, proof capture.
- **Blocker Report**: A diagnostic Business Artifact produced when an agent cannot create the expected deliverable, such as because an upstream handoff is missing or unreadable. A Blocker Report is visible to users and CEO Office, but it is not consumable by ordinary downstream tasks. _Avoid_: failed product brief, normal proof.
- **Direction Change Request**: A Business Artifact requesting an explicit change to a prior accepted business decision, such as changing the selected market, keyword, product category, MVP type, or launch target. Direction changes require Founder Approval before downstream work can consume the changed direction. _Avoid_: implicit pivot, engineering adjustment.
- **Founder Approval**: The user's explicit approval for high-impact business decisions, including changing the selected market or keyword, changing the MVP type, Engineering changing product direction, publishing to a public URL, submitting Google Search Console or sitemap actions, spending money, or connecting ads, affiliate accounts, or API keys. _Avoid_: CEO review.
- **Parent Proof Summarization**: The step where a parent task uses ready department subtask Proof to produce the parent-level Proof that can be reviewed by CEO Office. _Avoid_: automatic proof merge, subtask approval.
- **Proof Recovery**: A user-triggered or runtime-triggered attempt to turn existing Agent Output inside a controlled task workspace into recorded Proof after the original Agent Run finished without Proof. Proof Recovery must still satisfy the task's proof schema and must not treat arbitrary workspace files as completion. _Avoid_: auto-approval, hidden completion.
- **Task Recovery Request**: A user-triggered or runtime-triggered attempt to restart progress after a task failed, timed out, or became stale while running. A Task Recovery Request may requeue the original task when no Partial Output exists, or create a follow-up task from Partial Output when useful output exists. It is not Proof Recovery and it does not make work complete without Proof and CEO review.
- **CEO Review Request**: A department-submitted request for CEO Office to approve or return a valid, reviewable deliverable after execution. Departments can submit and track CEO Review Requests, but CEO Office owns the approve/return decision. Invalid artifacts, Blocker Reports, and decision requests are visible to CEO Office through separate queues, but they are not CEO Review Requests.
- **CEO Review Queue**: The CEO Office queue for valid, current, unreviewed Business Artifacts whose Artifact Kind is `deliverable` or `final_report`. _Avoid_: all review-status tasks, blocked queue.
- **CEO Decision Queue**: The CEO Office queue for Business Artifacts whose Artifact Kind asks for a decision, including ordinary decision requests and direction change requests. _Avoid_: deliverable review, artifact validation.
- **CEO Blocked Queue**: The CEO Office queue for tasks or Business Artifacts that cannot be reviewed because the artifact is missing, invalid, stale, blocked, or otherwise not reviewable. _Avoid_: review queue, approval queue.
- **Checkpoint CEO Review Request**: A CEO Review Request for an intermediate decision during task execution. Approval means the department may continue execution; it does not complete the task.
- **Completion CEO Review Request**: A CEO Review Request for final task acceptance. Approval means the task's submitted work is accepted and the task can be marked complete.
- **CEO Review Decision**: A durable CEO Office decision on a CEO Review Request. A decision can approve the work or return it with a structured reason and optional note. CEO approval accepts ordinary task work; it is not a substitute for Founder Approval when a direction change or external launch action needs user consent.
- **Review Return Reason**: A structured reason CEO Office chooses when returning a CEO Review Request. Current reasons are needs changes, unclear task definition, scope too large, and wrong direction.
- **Partial Output**: Useful Agent Output left behind by a failed or timed-out task. Partial Output should remain visible for diagnosis and follow-up, but it does not make the task complete.
- **Task Execution Profile**: A task execution contract that sets the expected time budget and failure explanation style for a task based on its deliverable shape. It is part of how Auto-Crop decides how long an agent should be allowed to work before the run is considered failed.
- **Effective Timeout**: The final timeout budget actually enforced for an Agent Run after Task Execution Profile and environment override rules are resolved. _Avoid_: displayed budget, requested timeout.
- **Task Execution Summary**: The latest durable outcome facts shown on a task, including failure reason, failure message, execution profile, and Effective Timeout. _Avoid_: activity text, run log.
- **Task Dependency**: A relationship where one task can only run after another task has an accepted, current, valid Business Artifact matching the downstream task contract. _Avoid_: task order, follow-up note, review-ready proof.
- **Department Subtask Readiness**: The point where a department-created subtask is ready to contribute to its parent task because it is in `review` and has recorded Proof. It is department-internal readiness, not CEO Office acceptance of the parent task. _Avoid_: subtask approval, parent completion.
- **CEO Task Dependency Graph**: A CEO Workspace projection that shows first tasks by owning department, user-facing status, and real Task Dependencies so the user can see what is blocked and where to inspect next. It is read-only and does not show department subtasks by default. _Avoid_: task list, department progress flow, editable task graph.
- **CEO Reassignment Request**: A department-submitted request asking CEO Office to clarify, split, replan, or reassign a task before or during execution. It is not a CEO Review Request because no Task Deliverable is being approved.
- **Consumable Business Artifact**: A Business Artifact that is current, valid, accepted through CEO Office review, not stale, not a Blocker Report, and not blocked by an unapproved Direction Change Request. _Avoid_: consumable proof, promising stdout, informal result.
- **Legacy Artifact Type Compatibility**: Temporary runtime support for reading the old `artifactType` field while the model migrates to Artifact Kind, Artifact Role, and Artifact Subtype. Compatibility lasts through the migration that adds the new persisted fields plus one cleanup migration. _Avoid_: permanent alias table.
- **Dependency Readiness**: The scheduler decision that all direct upstream Task Dependencies have accepted, current, valid Business Artifacts required by the downstream task contract, and that the full lineage chain remains valid. _Avoid_: dependency status check, proof existence check.
- **Dependency Cascade**: Runtime propagation that re-evaluates direct downstream tasks after an upstream task's Business Artifact is accepted by CEO Office, moving dependency-blocked tasks back to `queued` when all dependencies are ready. _Avoid_: manual refresh, automatic execution.
- **Bounded Recursive Cascade**: A Dependency Cascade that may continue through longer downstream dependency chains up to a fixed depth while preventing repeated visits to the same task. _Avoid_: unlimited cascade, scheduler wakeup.
- **Scheduler Wake Request**: A runtime hint asking the scheduler loop to tick sooner because dependency-derived work has become `queued`. It does not execute tasks, change Dependency Readiness, or bypass scheduler locking. _Avoid_: cascade execution, direct task run.
- **Bounded Recovery**: Automatic task recovery that changes execution conditions and has a hard stop, such as escalating an Effective Timeout before requiring replanning. _Avoid_: infinite retry.
- **Replan Required**: A task outcome where the current task is too broad or expensive for the available execution profile and should be split or rewritten before downstream work continues. _Avoid_: timeout failure.
- **Agent Activity**: Durable, user-facing timeline entries that explain task execution progress and outcomes. _Avoid_: debug log, raw stdout.
- **Emergency Stop**: The user-facing command that stops active Agent Runs and active Agent Sessions for a company without deleting queued tasks. _Avoid_: normal pause, task cancellation.
- **Artifact Workspace**: The workspace whose files are treated as the task's runnable or inspectable product. A dependent validation task may use another task's Artifact Workspace when validating that task's output. _Avoid_: task folder, temp folder.
- **Dependency Block**: A task state caused by an unmet or failed Task Dependency, distinct from an agent execution failure. _Avoid_: failed validation, skipped task.
- **Artifact Lineage**: The explicit chain of Business Artifacts and source decisions a task consumed, such as Founder Vision to Research findings to Product MVP brief to Engineering implementation to Growth launch plan. Downstream tasks must preserve lineage and may not silently swap business direction. _Avoid_: hidden context, workspace history.
- **Direction Drift**: A mismatch between a downstream Business Artifact and the accepted upstream business decisions it claims to implement. For example, an Engineering artifact implementing an image cropper when the accepted Product artifact specifies a JSON-to-CSV converter. Direction Drift blocks downstream consumption unless covered by an approved Direction Change Request. _Avoid_: creative interpretation, implementation detail.
- **Final Founder Report**: A CEO-owned Business Artifact and readable report that summarizes the original vision, actual result, department inputs and outputs, goal fit, drift status, remaining gaps, and recommended next step. A blocked workflow should produce a blocked founder report instead of leaving the user to infer the result from activity logs. _Avoid_: review list, activity feed summary.
- **Parent Task Aggregation**: Runtime aggregation that derives a parent task's dependency state from its direct department subtasks and ordinary Task Dependencies. It can queue the parent for proof summarization when all dependencies are ready, or block the parent when a dependency is blocked, failed, missing Proof, or needs replanning. _Avoid_: scheduler wakeup, automatic proof generation.
- **Company State Snapshot**: The persisted company, department, objective, task, proof, and review state needed to rebuild the dashboard after a refresh. _Avoid_: blueprint cache, frontend state.
- **Onboarding Wizard**: The sequential setup flow shown before a company is created. It collects company name, CEO Agent, Founder Vision, and Permission Mode one step at a time.
- **Creation Loading Page**: The CRT-styled intermediate page shown after `Create Company` while the backend waits for the CEO Agent to produce a blueprint.
- **Department Workspace**: The post-creation default view that shows a left rail of `CEO` plus generated departments, and a right-side role workspace for the selected role.
- **Reusable Retro UI**: Existing dashboard primitives under `apps/dashboard/src/ui/`, including `AppShell`, `PageHeader`, `Workspace`, `RetroPanel`, `RetroButton`, `RetroField`, `RetroTextarea`, `RetroSelect`, `RetroListRow`, `RetroBadge`, `RetroStatus`, `VideotexLog`, and `VideotexKeyValue`.

## UI Implementation Rule

New dashboard flows must reuse existing reusable retro components wherever possible. Create new UI primitives only when the existing component set has a clear gap, and prefer small composition components over new styling systems.
