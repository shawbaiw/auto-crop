## 1. 目标与范围

让部门从拆解、实施、验证到父任务汇总形成可验证的闭环：验证者能读取实际实施产物，验证失败会阻止业务验收，成功的内部交付无需 CEO 逐项批准，所有执行入口对依赖是否就绪给出一致答案。

认同“先保证结果正确，再保证流程可推进”的优先级，但四项修复应作为一个完整交付验收。只取消子任务审核或放宽关键词，会让负面验证报告被自动接受。

本次实施覆盖：

1. 子任务依赖与完整产物交接。
2. 结构化验证结果及其对消费、验收、返工的约束。
3. 内部交付与 CEO/Founder 决策边界，以及风险描述误触发。
4. 共享依赖就绪规则与 Task Hold 生命周期。
5. 当前进度、重复等待原因和操作入口的一致性。

本方案不要求重写调度器，也不通过修改 CLI 沙箱权限解决端口问题。真实 HTTP/浏览器验证若是任务要求，必须报告其实际结果；静态检查成功不能替代未完成的 HTTP 验证。

## 2. 已确认的产品策略与通用性约束

用户已确认：

- 修复对任意新建公司生效，不针对本次公司名称、愿景、行业或任务名称写补丁。
- 提供旧测试公司的独立恢复方案及 dry-run；提供方案不等于已经执行恢复，执行前展示具体差异并确认。
- 验证失败后默认进行自动有限返工、重新验证；超限或确需人类权限/决策时再进入人工处理。无需再询问这两个产品选择。

### 2.1 通用性审核结论

初版已经要求共享消费规则和结构化结果，但有三处容易误导实施：把当前三个子任务写成固定执行链、验证结果只支持单一目标、验收主要依赖网站案例。修订后，以输入/输出契约驱动的任务图、多目标版本绑定和跨业务新建公司测试替代这些限制。当前故障只保留作证据与反例。

runtime 根据结构化的生产者/消费者关系、产物角色、验收要求、动作意图和状态事实决定行为。公司 ID/名称、愿景文本、部门展示名、任务标题、特定服务名及样例文件名，只能作为业务数据或 fixture，不能成为调度、风险豁免、验收或恢复的专用分支。

公司创建/blueprint、后续任务规划、部门拆分、重新规划均需产出同一消费契约；创建公司时不能要求用户知道或手工填写内部结构。生产者匹配不到、契约缺失或含环时，在规划校验/调度准备阶段给出可修复错误，不能猜一个工作区继续执行。按 Task Type/Artifact Role/Proof Schema 注册业务契约是允许的扩展；依据本次样本文本追加判断不是。

新建公司必须在没有旧公司数据、恢复脚本或手工依赖修补的前提下通过验证。旧公司恢复成功不能替代新流程验收。

## 4. 一次声明、各处复用的业务规则

实施前阅读 `CONTEXT.md`、`apps/server/CONTEXT.md`、ADR 0007、0017、0020，以及产物交接和能力授权相关 ADR。实施完成时更新受影响的定义及 ADR 修订，使本文的新增契约有正式归属。

### 4.1 区分四个结果

| 结果 | 表达什么 | 不足以证明什么 |
| --- | --- | --- |
| Agent Run 正常结束 | agent 进程与运行协议正常结束 | 工作目标达成 |
| Business Artifact `validationStatus=valid` | 交付结构、来源等契约有效 | 被测试产品验证通过 |
| 验证业务结果 | 对指定产物版本、指定要求的检查结论 | 其他版本或其他要求也通过 |
| 业务验收/内部可消费 | 当前消费者在其权限与用途下可使用交付物 | 所有消费者都可使用、父任务已经完成 |

保留负面验证报告作为有效诊断证据；其“报告有效”与“不能作为成功交付向下游放行”同时成立。进程正常结束可继续记录为成功，但任务目标与完成事件不能伪报已通过。

### 4.2 内部消费与普通消费

由一个共享的依赖解析入口识别消费关系；调用方不自行选择宽松或严格模式。

- 同一公司、同一父任务下声明的子任务依赖，以及父任务汇总其直属子任务，属于内部消费；公司/父级归属和输入契约均需校验，不能仅因生产者是 subtask 而放行。跨公司引用应拒绝。
- 跨父任务、跨部门、无对应亲缘关系的依赖属于普通消费。
- 内部成功交付采用 `review` + 当前有效 Proof/Artifact + 对应业务条件满足；这表示内部就绪，不要求逐项 CEO 验收。
- 普通消费保留 `complete` + 当前已验收 Business Artifact 的门槛。
- 任一路径都检查真实的未决 Founder Decision、Founder Approval、人工动作、失败、过期版本等阻塞条件；`review + Proof` 不是通用放行捷径。
- 内部交付不得独立调用父任务的 KR 达成逻辑。父任务汇总并验收后，才产生相应父级成果。

## 5. 建立真实的执行链与产物交接

### 5.1 图结构

依赖方向以下游指向上游存储。以已声明的输入/输出契约构造有向无环图，支持单任务、不同数量的子任务、顺序依赖、并行分支和多输入汇合。某任务仅等待实际需要的生产者；验证节点覆盖其验收范围内的全部目标。当前三阶段模板只是其中一个实例：

```text
已验收的外部上游 → Define → Execute → Validate → 父任务汇总 → 普通下游
```

父任务声明汇总所需的子产物与验证结果，不假设恰好有三个子任务。当前模板可以保留其三个汇总依赖；其他模板按实际契约生成。创建子任务时，先快照父任务原有外部依赖，再按输入契约添加父子、兄弟依赖，避免继承过程中形成环。子任务的阶段角色应由结构字段/类型承载，不能用英文标题或数组排序推断。当前只支持一层父子任务；无需为本修复新增递归层级，但对不支持的结构应明确拒绝。

完成条件：任意消费者不能在所需生产者尚未就绪时执行，多输入节点必须等待全部必需输入；互不依赖的分支保持可并行。当前实例中的 Execute 等待 Define、Validate 等待 Execute。并发调度、任务重命名或节点排序变化不能改变依赖语义；同级内部消费与父级汇总复用第 4 节契约。

### 5.2 消费完整、可追溯的实施产物

扩展现有 Handoff Package/manifest 机制，按明确的依赖与产物角色选择输入，不再从依赖中取第一个 `artifactWorkspacePath` 作为隐式输入。

推荐保持独立工作区，将指定生产者的完整产物快照放入消费者明确的输入目录。验证输出写在自己的报告目录；验证过程中需要构建或生成文件时，使用该快照的工作副本，不修改已发布的生产者快照。

交接契约至少记录生产任务、当前 artifact/proof、产物版本或内容摘要及角色；文件型附根目录和相对清单，数据型附可读取的数据快照或资源引用。版本标识由 runtime 根据实际产物建立，不能只信 agent 自报。

产物完整性由任务的交接契约定义。交付形式可为文件集合、结构化数据或可验证资源引用；消费者通过对应 collector/manifest 获得所需内容，不能假设每种产物都有代码工作区。网站案例需要页面、脚本、样式、配置等文件；数据分析案例需要数据快照、处理结果与指标证据；内容任务需要正文及其引用材料。网站不能只复制一个 `index.html`，但也不能把网站文件清单强加给其他业务。复用已有 collector，但明确补足其当前仅复制 Proof 文件的不足；限定在授权工作区与声明文件范围，排除凭据、缓存及无关内容，并拒绝越界路径/符号链接。

输入缺失、版本不符或文件不可读时，形成具名的交接错误，指出生产者和缺失内容；先修复/重新交接，再运行验证，不能启动到空目录后把报告的正常退出当成成功验证。

完成条件：文件型与结构化数据型的集成测试均能让验证者读取契约指定的完整版本；任一必需输入缺失都不能得到通过结论。多文件站点只是其中一个 fixture。

## 6. 让验证结论成为可执行契约

针对承担验收职责的 validation task/产物角色，增加并校验结构化验证结果。示例字段名可调整，但语义固定：

```ts
type VerificationResult = {
  outcome: "passed" | "failed" | "inconclusive";
  contractRevision: string;
  targets: Array<{ taskId: string; artifactId: string; revision: string }>;
  checks: Array<{
    requirementId: string;
    outcome: "passed" | "failed" | "not_run";
    evidenceRefs: string[];
  }>;
};
```

必验要求来自规划时声明、runtime 校验的任务/Proof Contract，来自相应任务类型或产物角色的契约，不是固定首页/SEO 检查项。计划、执行提示、验证提示和验收代码读取同一契约版本；验证 agent 不能任意删减或把失败项标成可选。runtime 核验非空且完整的目标集合、目标关联、产物版本、契约版本、必验项覆盖、结果一致性和可读取证据；不能用空 checks/targets 得到通过。多生产者中任一必需产物更新都会使原验证失效。命令类检查使用执行记录中的退出码，数据/文档类检查使用其对应证据。文字结论用于解释，不作为正则猜测的判定源；结构化结果的校验也不宣称能自动证明任意自然语言愿景完全达成。

- 全部必验项通过，且目标是当前版本，才可得出 `passed`。
- 任一必验项失败，不能标记 `passed`。
- 未执行、环境无法完成、缺证据、旧格式缺结果字段时，不能默认为通过。
- 已有环境受限降级契约仍有效：只有明确允许的替代证据满足同一要求时才能通过，保留局限；不能把必需项全部跳过。
- 非验证类的普通研究报告不强制套用该字段，避免泛化破坏其他任务类型。

将“报告可读/格式有效”和“允许成功消费/验收”做成不同判定，在 scheduler 完成、自动验收、CEO approve、Founder Decision 接受、refresh/proof recovery、review reconciliation、dependency cascade、父级汇总等实际入口复用。手动批准不能把 failed/inconclusive/stale 验证结果改成 passed；需要改变验收范围时走明确重规划并重新验证。

对旧验证报告保留可读性，但不从自然语言推造通过结果。对于仍在活动流程中、缺乏新契约的旧验证产物，要求重新验证或走显式恢复；不要对所有历史 complete 任务做隐式回滚。

完成条件：同一份结构有效但验证失败的报告，经任一入口都不能变成成功交付；版本 A 的通过报告无法为版本 B 放行。父任务也不能通过生成一段“成功总结”绕过其当前子验证失败。

## 7. 验证失败后的路径

执行已确认的自动有限返工策略。保存负面报告和来源版本；父任务及其普通下游停在具名依赖/返工状态；按失败 requirement/target 映射到责任生产者，不按任务标题决定返工对象。

1. 区分交接故障、实现缺陷、执行环境不足。交接故障优先修复交接并重跑验证；产物缺陷将失败检查项作为反馈输入给对应生产任务（当前实例为 Execute）；环境不足走已有能力/人工动作路径。
2. 反馈采用单独的返工关系/记录，而不是给生产任务添加对其失败验证者的普通依赖，以免形成环。
3. 责任生产任务产生新版本后，使相关旧验证失效并重新验证；多生产者时只返工受影响的生产者，并保留未变更的输入版本。并发中的旧验证结果不能解锁父任务。
4. 业务返工必须有持久化上限。现有 `MAX_TASK_ATTEMPTS=3` 针对失败 Agent Runs，不能直接假定它覆盖“进程成功、验证失败”的循环。本方案默认最多 3 次验证轮次（含首次，即至多两轮自动返工）；这是统一 runtime 策略默认值，不是当前公司的特例。对同一父任务下的同一验收目标集合/契约建立持久化返工预算，多分支汇合验收共用其预算，重复事件不重复计数；自动产生新版本、刷新或重启不能重置该预算，显式重规划才开启新预算。
5. 超限复用 Bounded Recovery 的可操作出口与历史保留原则，提供返工/重规划入口，不无限创建新子任务。

首次可修复的验证失败自动进入返工；只有预算耗尽、确需人工授权/选择或已识别为自动无法处理的环境约束时，才升级人工处理。人工入口不提供把负面验证直接批准为通过的操作。

完成条件：失败→自动返工→新版本复验可成功闭环，连续失败则有界停止；负面报告不会通往普通成功下游，重启后仍保留原因与计数。

## 8. 审核边界、风险与 Hold

### 8.1 内部就绪不是 CEO 待审

正常内部交付留在 `review` 时，用显式的部门内部汇总 Hold 表示其归属，例如新增 `awaiting_parent_aggregation`，resolver 为 runtime、subject 为父任务。这样既满足 ADR 0020 的 parked implies held，也不会被 reconciler 补成 `awaiting_ceo_review`。

内部消费判定明确认可该 Hold，不把它当作阻止兄弟消费的未决业务决策。父级汇总完成后，给子任务定义明确的收尾转换，清理内部 Hold；不伪造 CEO approval、不重复产生 KR 达成。子任务可作为内部归档完成，但未被业务验收的内部 Artifact 仍不能被普通依赖消费。

新增 Hold 时同步更新 exhaustive 类型映射、状态绑定、affordance、执行路由、界面呈现与覆盖测试。任何对 review 的 fallback、状态读取时的 reconcile、refresh/recovery 都必须识别内部就绪，反复读取不能重建 CEO 待审。

CEO 投影和 approve/return guard 使用同一个服务端资格判定，正常子任务没有 CEO completion review 操作。CEO 仍可查看部门过程；真实决策、风险和超限阻塞仍应可见，不能按 taskKind 一刀切隐藏所有消息。

### 8.2 描述风险不等于请求执行风险动作

将待执行或请求批准的动作与报告中的背景、未做事项、局限、未来建议分开。用结构化 action intent 描述动作类型、目标、是否属于当前执行范围，以及对应审批。实际外部动作继续受现有 Founder Approval/能力授权约束，子任务身份不构成豁免。

新交付物的自动验收优先使用经校验的动作声明；同类问题适用于部署、付款、账号、凭据、数据等所有既有风险类别，不以 Search Console 为唯一例外。不能对整个 payload JSON 扫到服务名就送 CEO；也不能删除整个 payload 扫描后，允许实际发布/提交索引动作漏过。现有 capability/pre-dispatch enforcement 保持有效，未声明不能视为已授权。

复用现有可表达此语义的字段；不足时增加小范围动作契约，并同步 schema、prompt、capture 与消费端。明确真实风险的处理表：当前待执行动作需要批准时阻塞对应执行；内部报告提出的未来动作进入父级汇总/后续计划，不立即要求批准一个并未执行的动作。若证据显示已执行未授权动作，保留异常并升级处理，不能事后自动洗成普通成功交付。

旧文本缺乏可信动作声明时不得靠英文单词或宽泛否定词例外推造语义；活动旧产物按兼容路径补录/重跑，无法判断的真实动作保持显式未决。风险请求需继承至父级决策上下文，并防止同一动作在每个子任务重复请求。

完成条件：中英文的“未接入/以后考虑 Search Console”不产生当前审批；明确要求现在部署、提交 sitemap、连接账号等仍保留正确审批约束；审批信息不会因内部交接丢失。

## 9. 统一就绪判定与进度呈现

以 `resolveDependencyReadiness` 或等价共享模块为唯一消费判定入口，内部返回关系类型、就绪/阻塞原因、精确上游与 artifact 版本、可用 handoffs。父级 aggregation 只负责汇总与转换，不再实现另一份 `review/complete` 判定。

逐项审计 scheduler、parent aggregation、dependency cascade、hold reconciliation、refresh、recovery、CEO 决策后的唤醒路径。它们必须对同一事实给出一致结果。状态变更继续经过 `applyTaskTransition`，只解除本次事实实际解决的 Hold；新事件取转换后的实际状态，不能用请求中的 `queued` 代替转换结果。

UI 按服务端当前状态/holds/affordances 展示一致的当前阻塞原因集合；旧 queued 事件保留为历史，不显示为当前可执行事实。同一任务因不同 subject 的 Hold 提供不同操作可以保留，但同一 affordance/subject 在同一区域只绘制一次。

对任意任务，逻辑等待身份基于任务、Hold kind、subject，不能以易变的原因文本制造新等待。本次 Capture 的两条开放 Hold 可作为回归样本，不能据该任务 ID 定向去重。同一阻塞原因变化时更新呈现，保留必要审计，不增加第二个当前按钮。

用服务端快照及模拟 SSE 更新复现进度问题，分别覆盖无浏览器刷新、全量重载、旧事件晚到。CEO 的可操作数据与实际页面按钮两层均测试，不把截图当作根因证据。

完成条件：连续调度 tick、状态 GET/reconcile、refresh 和页面重载都不产生 queued/waiting 抖动；父任务等待时给出真实阻塞者，旧事件不能重新激活过期操作。

## 10. 旧测试公司恢复边界

已确认提供旧公司恢复方案。代码交付中提供显式接收目标公司 ID 的独立 dry-run，列出缺失依赖、待重新交接的版本、需要 supersede 的验证报告、需要转换的误建 CEO Holds，以及会重跑的任务。执行恢复前由用户确认具体差异。

恢复工具依据结构化契约及现存产物识别缺陷，不把诊断公司的 ID、任务名、工作区路径写死在生产修复中。本公司 ID 仅作为操作参数；无法可靠识别旧图中角色或输入关系时，dry-run 明确要求重规划，不凭标题猜测。

恢复顺序：备份数据库与产物、确认相关 run/锁已停止 → 修复图结构与完整交接 → 重跑对应验证任务 → 按新结果自动有限返工或汇总 → 恢复普通下游。已有生产产物完整时先重新交接验证，避免无条件重写。

恢复操作走受约束的 runtime 转换，具备幂等性、并发保护和审计；保留历史审核/运行/负面报告。真实 Founder Decision、审批或人工动作 Hold 保留。不要在 GET/state 中偷偷执行破坏性迁移，也不要把三个子任务批量改为 accepted 作为恢复方案。

## 11. 实施顺序与完成证据

| 步骤 | 工作 | 完成条件 |
| --- | --- | --- |
| A | 在隔离 fixture 中重现故障，并覆盖不同业务与任务图 | 测试明确因这些缺陷失败，不调用真实 agent 或污染测试公司 |
| B | 定义验证结果、内部消费、角色与版本契约 | 数据模型、兼容行为及 Hold 状态表清晰；负面/过期结果无法成功验收 |
| C | 依赖链、完整产物交接及验证输入 | mock agent 生成不同类型产物，多输入验证者能读取指定版本；缺输入则准确失败 |
| D | 实现自动有限返工与超限/真实人工依赖出口 | 正负路径与上限均可复现，重启不清空预算 |
| E | 将全部调度/验收/恢复入口接到共享判定，落实审核与风险边界 | 正常内部结果零 CEO completion review；真实审批不丢失；无状态抖动 |
| F | UI、重复 Hold、历史兼容与恢复 dry-run | 页面/API 一致；旧数据按用户范围处理；dry-run 不写状态 |
| G | 更新正式文档、运行回归与类型检查、提交实现说明 | 每项验收有测试证据，说明剩余限制，不以测试全绿代替真实链路证明 |

可以按步骤提交，但 B–F 的中间实现不得单独作为已解决本次问题交付。

### 必须覆盖的回归场景

1. 成功图：分别覆盖单任务、顺序链、并行生产者→多输入验证→父级汇总→普通下游；无正常子任务人工审核，父级成果只计一次。当前三阶段模板作为其中一例。
2. 原始反例：负面报告结构有效、必验项全 false、文本含 Search Console；移除该词后仍被业务结果拦住。
3. 交接损坏：缺 JS/CSS、manifest 目标错误、不可读文件、越界路径，不放行验证或父级成功。
4. 顺序与版本：并发调度不提前执行；返工后的新实现不能消费旧验证；旧验证晚到不解锁。
5. 关系边界：同父级兄弟可内部消费；跨父级/部门普通依赖仍要求 accepted。
6. 决策边界：内部就绪携带真正 Founder Decision/Approval 时仍阻塞；只解除内部 Hold 不清掉其他 Hold。
7. 入口一致：自动验收、CEO approve、Founder Decision 处理、refresh、recovery、reconciliation、cascade 都不能绕过失败验证。
8. 返工：首次可修复失败自动返工，随后通过能继续；连续失败在统一默认上限停止，重启和自动新版本不重置；重复完成事件不多次调度/计数，进程成功退出不能逃过业务返工计数。
9. 风险：中英文否定/未来描述不误触发；当前真实外部动作仍需授权；同一请求不因三个子任务重复出现。
10. Hold/UI：反复状态读取不重新生成子任务 CEO 审核；queued 历史不覆盖当前等待；同一操作不重复，人工出口真实可用。
11. 兼容：缺新验证字段的活动旧报告不默认通过；历史记录保留；恢复 dry-run 及执行在副本上验证幂等。

### 从新建公司验证通用性（交付必需）

增加至少三类独立 fixture：网站/应用产物、数据处理与结果核验、文档/内容与引用核验。每类均从公司名称与愿景输入开始，经实际创建入口、blueprint 持久化、拆分、调度和交接完成验收。mock adapter 可以稳定返回领域不同的规划/产物，但必须遵守生产 schema；不能手动插入正确依赖后宣称创建链路通过。

- 每次创建新公司、新任务 ID 和空工作区；测试不依赖原公司数据库，也不调用恢复工具。
- 对同一业务意图改公司名、同义改写愿景、切换中英文任务展示名；核心验收不变量不变，不要求 LLM 生成完全相同的任务图。
- 改成真正不同的愿景/产物类型、增加节点、交换无依赖节点顺序、引入并行和多输入；按声明契约执行，不强制三阶段或网站文件清单。
- 至少一类完全不提 Search Console；仍需覆盖成功、业务验证失败后自动返工和超限路径。
- 审查生产 diff 中新增的样例 ID、任务标题、公司/愿景文本、服务名条件分支。仅 fixture、证据说明和显式恢复参数允许出现诊断样例；服务类别注册应是契约能力，不是名称例外。

本次旧公司恢复通过、新建公司仅手工修表后通过、或只测共享函数而未走创建入口，都不满足通用修复的验收要求。

针对上述场景先运行相关 Vitest 测试，再运行仓库 `pnpm test`、`pnpm typecheck` 和适用的 mock smoke。真实 agent 验证需要独立的新测试公司或获准的恢复环境，不默认改动本次原公司。最终报告说明所用分支、命令、正反例结果、是否执行旧公司恢复，以及本地端口/浏览器验证是否实际完成。

## 12. 主要代码入口

- 公司创建/blueprint 校验、任务规划及 replan 的实际入口：统一输出角色、输入关系和验收契约；从调用链定位，覆盖新建公司。
- `apps/server/src/runtime/scheduler.ts`：拆分、继承依赖、工作区选择、完成与审核分支。
- `apps/server/src/runtime/proof.ts`：Proof 收集与 Handoff Package 完整性。
- `apps/server/src/runtime/businessArtifact.ts`、`automaticAcceptance.ts`、`businessAcceptance.ts`：结构有效、业务结果与验收边界。
- `apps/server/src/runtime/dependencyReadiness.ts`、`parentTaskAggregation.ts`、`dependencyCascade.ts`：共享消费规则。
- `apps/server/src/runtime/taskTransition.ts`、`taskHoldReconciliation.ts`、`taskAffordances.ts`、`boundedRecovery.ts`：状态、Hold、出口与预算。
- `apps/server/src/runtime/taskRefresh.ts`、`taskRecovery.ts`、`reviewReconciliation.ts` 及实际 CEO/Founder 决策处理函数：替代验收入口。
- `packages/core/src/ceoOffice.ts`、`taskHold.ts`、`types.ts`、`schemas.ts`：投影及共享契约。
- `apps/dashboard/src/pages/DepartmentWorkspace.tsx` 与状态同步/操作控件：当前状态、入口、历史事件。
